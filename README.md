# Recipe Finder

A beginner-friendly full-stack recipe discovery application. Users can search by recipe name, filter by category, match recipes against ingredients they have, create accounts, and save favorites. Administrators can add, edit, and delete recipes and view registered users.

## Problem and objectives

People often have ingredients at home but are unsure what meal to cook. Recipe Finder helps them discover practical recipes using those ingredients. The learning objectives are to understand HTML/CSS/JavaScript, REST APIs, Express middleware, PostgreSQL relationships, password hashing, authentication, and role-based authorization.

## Roles and features

- **Guest:** browse, search, filter, and view recipe steps.
- **Registered user:** sign up/sign in, save/remove favorites, sign out.
- **Admin:** all normal recipe browsing plus recipe create/edit/delete and registered-user listing.
- Search supports recipe name, category, and comma-separated ingredient terms. Ingredient matching is simple case-insensitive text matching, not a nutritional or AI recommendation system.

## Technology stack

HTML5, CSS3, Vanilla JavaScript, Node.js, Express, Supabase PostgreSQL, `@supabase/supabase-js`, `bcryptjs`, `jsonwebtoken`, `dotenv`, `helmet`, and `express-rate-limit`.

## Setup on Windows

### 1. Open the project

Extract the project ZIP. In VS Code choose **File → Open Folder** and select `recipe-finder`. Choose **Terminal → New Terminal**.

### 2. Install dependencies

```powershell
cd backend
npm install
```

This installs the packages listed in `backend/package.json` and creates `backend/package-lock.json`.

### 3. Create a Supabase project

1. Sign in to Supabase and create a project.
2. Open **Project Settings → API** (or the project's API keys page).
3. Copy the project URL and the server-side `service_role` key. Treat the service-role key as a password.
4. In the Supabase dashboard open **SQL Editor → New query**.
5. Copy all of `database/schema.sql` into the editor and click **Run**.
6. Open **Table Editor** and verify `users`, `recipes`, and `favorites` exist. The `recipes` table should contain three starter recipes.

### 4. Configure backend environment

Open `backend/.env`. Replace the placeholders:
- `SUPABASE_URL`: your Supabase project URL.
- `SUPABASE_SERVICE_ROLE_KEY`: the server-only service-role key.
- `JWT_SECRET`: a strong random string of at least 32 characters.
- `ADMIN_EMAIL`: leave as `mrec@gmail.com` if that is your designated admin.
- `ADMIN_PASSWORD`: set the requested demo password `MREC@123` only for a local classroom demo, or choose a stronger private password. Do not publish it.

Generate a JWT secret from a terminal in the `backend` directory:

```powershell
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
```

Copy the output into `JWT_SECRET`. The `.env.example` file documents variable names with placeholders; it is safe to commit. The real `.env` file is ignored by Git.

### 5. Create the administrator account

In `backend/.env`, set `ADMIN_EMAIL=mrec@gmail.com` and set `ADMIN_PASSWORD=MREC@123` to use the requested demo login. This is a weak, publicly disclosed classroom password: use it only for a local demo, and replace it with a strong unique password before deployment. Then run from `backend/`:

```powershell
npm run create-admin
```

Expected output says that the admin account was created or updated. The script hashes the password before saving it. It does not create an admin from browser-side code.

### 6. Start the application

From `backend/`:

```powershell
npm start
```

Expected output:

```text
Recipe Finder running at http://localhost:3000
```

Open [http://localhost:3000](http://localhost:3000). Do not open `index.html` directly as a file; use the Express server so `/api` requests work.

### 7. Check the database connection

Open [http://localhost:3000/api/health](http://localhost:3000/api/health). Expected JSON:

```json
{"status":"ok","database":"connected"}
```

If it returns HTTP 503, check the project URL, service-role key, and whether `database/schema.sql` ran successfully.

## Architecture

The browser sends `fetch()` requests to the same-origin `/api` endpoints. Express validates the input and verifies JWTs for private routes. It checks the user's role in PostgreSQL before admin actions. The Supabase client is initialized only in the backend. The service-role key bypasses PostgreSQL RLS, so Express authorization is mandatory. RLS is enabled with no browser-facing policies because this project intentionally routes all database access through Express.

Passwords are hashed with bcrypt. The backend returns an eight-hour signed JWT; the demo frontend keeps it in `localStorage` for ease of learning. This is a simpler classroom setup, but an XSS vulnerability could expose a token. For production, consider an HttpOnly, Secure, SameSite cookie design with appropriate CSRF protection, HTTPS, and a reviewed deployment configuration. Do not use this development setup as-is for sensitive production data.

## API reference

All successful responses are JSON. Private endpoints require `Authorization: Bearer <token>`.

| Method | Path | Purpose | Access |
|---|---|---|---|
| GET | `/api/health` | Check server/database | Public |
| POST | `/api/auth/signup` | Create account | Public; body `{name,email,password}` |
| POST | `/api/auth/signin` | Sign in | Public; body `{email,password}` |
| GET | `/api/auth/me` | Current account | Signed-in user |
| GET | `/api/recipes` | List recipes | Public |
| POST | `/api/recipes` | Create recipe | Admin |
| PUT | `/api/recipes/:id` | Update recipe | Admin |
| DELETE | `/api/recipes/:id` | Delete recipe | Admin |
| GET | `/api/favorites` | List current user's favorites | Signed-in user |
| POST | `/api/favorites` | Save a favorite; body `{recipe_id}` | Signed-in user |
| DELETE | `/api/favorites/:recipeId` | Remove a favorite | Signed-in user |
| GET | `/api/admin/users` | List up to 200 accounts | Admin |

Common errors: `400` invalid input, `401` missing/invalid login, `403` insufficient role, `404` missing resource, `409` duplicate email/favorite, `429` too many login attempts, and `500` unexpected server failure.

Recipe create/update JSON:

```json
{
  "name": "Tomato pasta",
  "description": "A quick dinner",
  "category": "Dinner",
  "cooking_time": 25,
  "image_url": null,
  "ingredients": ["200 g pasta", "2 tomatoes"],
  "steps": ["Boil the pasta", "Cook tomatoes and combine"]
}
```

## Using the application

1. Browse starter recipes on the home page.
2. Search a recipe name, choose a category, or enter comma-separated ingredients such as `tomato, onion`.
3. Click **View recipe** for ingredients and preparation steps.
4. Create an account and click a heart to save/remove a favorite.
5. Sign in as the admin to see the recipe management form. Add a recipe; use Edit/Delete on recipe cards. Use **Load users** to see account email and role.

## Testing checklist

- [ ] `/api/health` returns database connected.
- [ ] Starter recipes appear on the home page.
- [ ] Search by name and category filters results.
- [ ] Ingredient search finds recipes containing a matching term.
- [ ] Sign-up with valid details creates an account.
- [ ] Reusing an email returns a duplicate-account error.
- [ ] Invalid email or short password is rejected.
- [ ] Sign-in succeeds with correct credentials and fails with incorrect credentials.
- [ ] Signed-out users cannot save favorites.
- [ ] A user can save and remove a favorite; favorites remain after reload/sign-in.
- [ ] A normal user cannot create, edit, or delete recipes or list users.
- [ ] Admin can add, edit, and delete recipes.
- [ ] Recipe forms reject missing ingredients/steps, invalid category, and out-of-range cooking time.
- [ ] Layout remains usable on mobile widths.
- [ ] Sign out removes the local token and private UI.

## Troubleshooting

- **`Missing SUPABASE_URL`**: edit `backend/.env`; ensure you started Node from the backend project and the file exists there.
- **JWT secret error**: generate a long random secret and replace the placeholder.
- **Health endpoint returns 503**: run `database/schema.sql`, verify the Supabase URL/key, and inspect the backend terminal.
- **`relation does not exist`**: the schema did not run in the expected Supabase project.
- **Port already in use**: change `PORT=3001` in `.env` and visit `http://localhost:3001`.
- **Admin dashboard not visible**: run `npm run create-admin`, then sign out and sign in again.
- **No favorites**: ensure the user is signed in and the recipe still exists.
- **Supabase key accidentally exposed**: rotate it immediately in Supabase. Removing it from the latest commit is not enough if it was already pushed; clean repository history as appropriate.

## GitHub upload

Run commands from the root `recipe-finder/` folder:

```bash
git init
git status
git add .
git status
git commit -m "Build Recipe Finder"
git branch -M main
git remote add origin YOUR_GITHUB_REPOSITORY_URL
git push -u origin main
```

Create an empty repository on GitHub first, then replace the remote placeholder with its HTTPS or SSH URL. Before `git add .`, confirm that `backend/.env`, `node_modules/`, and private data are ignored. `backend/.env.example` should be committed. If a secret was already committed, rotate it immediately; `.gitignore` does not erase Git history.

## Limitations and future improvements

This MVP uses simple ingredient substring matching and starter recipes. It does not call external recipe APIs, calculate nutrition, upload images, send password-reset emails, or provide email verification. Images are optional URLs and the app works without them. Future improvements could add ingredient normalization, pagination, recipe ratings, password reset, secure cookie sessions, and a reviewed production deployment.
